A new 20-second combat observation on accepted motion_combo05 chose normal r01b through the real route controls, instead of repeating the prior mixed-shooter route. It passed the unchanged guard (wall39.152300, gap0.060074), cleared that combat room, and recorded47 frames with no visual errors. Actual frames23 and32 show shield enemies still presenting the shield to screen-right while source aim/facing points left toward the moving player. Frame32 has aims(-0.553066,0,-0.833137) and(-0.980729,0,-0.195373). This is not just ornamental: enemy_director.guard_multiplier tests the real facing with dot>=0.65 for frontal mitigation; guard turning is deliberately limited to support flanking. A fixed-right shield obscures that existing counterplay.

The isolated presentation-only candidate reads armored facing and mirrors the existing body at its original foot anchor. It uses the same signed body_scale for visible sprite, hit flash and alpha-exact picking, retaining latest motion_combo05 targeting. No gameplay rules, facing rate, cooldown, hit region, damage, AI, or other hero is changed. No text/ring or new hint substitutes for body direction. Current shield artwork can only express left/right, not an exact eight-direction guard arc, so no such precision is claimed.

Candidate first launch stopped immediately with GuardError:unowned_engine_detected_no_signal_to_it. Its owned processes were cleaned up; no unrelated engine was signalled. There are no functional candidate observations and no acceptance claim. motion_combo05 remains the accepted baseline, Q3 remains separate. Next steps: identify/avoid other owned workloads, actual left/right guard behavior and pixel-picking review, necessary UI and whole-floor regression before integration.

Broader scene audit: hero remains distinct from pink/dark enemies, including clustered guard/minion frames; platform edges did not hide the hero in reviewed frames. Earlier mixed-route frames show readable hostile projectiles. A minor warning-pointer/own-HP-bar overlap was noted, but not used to justify another cosmetic revision. No evidence warrants changing camera or authored obstacle geometry.

Any future change should read existing guard_active/guard_broken_left and animate the shield using available art, rather than inventing damage rules or filling the screen with labels. Need actual blocked-versus-broken combat comparison before implementation.
