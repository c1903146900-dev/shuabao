# Approved minimal inventory entry integration

2026-10-08. Approved implementation plan; unfinished steps are not acceptance.

1. Freeze a closed save-profile registry: old4 exact terrain validator/base Store; new5 exact inventory validator/bounded Store. No arbitrary plugin callbacks or script paths. Existing v1 slot index and old save bytes remain unchanged. A new5 slot has a strict immutable slot-profile marker outside its world directory; publish index only after verified marker creation. Interrupted creation must not appear as a playable half-slot. Missing marker means legacy4; malformed/unknown marker rejects.
2. Add cold schema5 validation that derives a temporary Core from the candidate's validated world ID while retaining actual catalogue/protocol configuration. Store world-marker checks and whole-state validation precede any authority/world/actor/inventory restore. Do not bind validation to the startup authority's temporary random world ID. Inspection remains read-only.
3. Keep the same exact terrain owner script/SourceLease. A private inventory service owns Core and temporary access scopes; no mutable Core escapes through views. At a confirmed Frame boundary, the authenticated bounded inventory queue applies atomic in-memory actions after the previous Actor confirm and before new submit/auto/stop save. Validate final combined envelope budget before publication.
4. Action acknowledgement is authoritative, not durable. Preserve cursor/revision and exact epoch/connection incarnation; reject unreceived transport sequence jumps and stale/replayed packets. Rejected intents consume only the transport receive cursor, not an item mutation. A new connection destroys old pending/cache and never resends an old unresolved command automatically. Profile is derived from authenticated peer, not packet fields.
5. Frame remains the sole actual Store writer/receipt authority. Register exact schema5 bindings; all initial/join/auto/normal-shutdown saves include inventory and cursor. Freeze/compare inventory and actor lineage before/after saving. Main-not-committed and main-committed/backup-failed retain their existing distinct semantics. No compensating replay. New real profile gets an empty bag; resumed missing inventory rejects.
6. F10 must prove both actor and inventory cutoffs/pending/queues drained. Actor cutoff alone is insufficient. Per-player inventory views are privately sent inside authenticated versioned epoch envelopes, never broadcast with the full private component.
7. Actual acceptance: UI36 finite tests first, then focused modules/old4 regressions, then ordinary new5 empty bag, isolated fixture actual mouse take/place/merge and save/reopen, and old4 Continue. Fixture items are not ordinary grants and do not export. Initially place carried fixture items back before closing; this is a test precondition, not a decision on disconnect carry policy.
8. Linux finite validation may precede Windows. Windows5 must get an explicit generation-storage record/config registration and the corresponding failure matrix within this delivery stage. Until then Windows5 rejects rather than falling back to unsafe rename. Linux-only candidate is not the user's Windows playable package.

Four user choices remain pending: Q quantity, right-click half-return into an occupied/full original slot, world-drop merge radius, and disconnect carry disposition. Do not install defaults. Ordinary new5 currently has empty inventory, so it is not yet the full acquisition/player loop. See `012_FIRST_REAL_ITEM_DEPENDENCIES.md` for the separately sourced tree/harvest/drop/pickup dependency, with no invented starting gift.

## Forward-compatible rule updates

Source SHA is an audit/provenance pin, not by itself the permanent gameplay semantic version. Later rule updates must use an explicit schema/rule-semantic version and per-instance validity checks. An additive content ID change with unchanged old-ID semantics should admit a safe forward path; do not create another world schema merely to add seeds or make old saves permanently unusable on each table edit. For changed old semantics, plan a bounded explicit migration: retain original bytes, validate each stack/current instance against the relevant old/new rules, preserve counts/IDs/opaque instance state when valid, reject/quarantine incompatible cases visibly without swallowing items. This current entry slice retains source pins and original files while the minimum compatible rule-version path is implemented; it is not a final universal hash-equality compatibility policy.
