# Rejected-shop input continuity, accepted as motion_combo09

Actual first-room native keyboard/mouse observation on motion_combo08 exposed a player-facing control loss: pressing P during combat refused the shop but cleared held movement and basic attack. A600ms moved x6.679064 to3.079067; a following A+P600ms remained x3.079067 while enemies kept warning/attacking. E1 marking/recast and normal moving basic were also observed; no basis was found to change their existing rules.

Cause: host._shop unconditionally suspended input before asking session.open_panel, whose combat eligibility check rejects the request. Fix removes only that preemptive call. Accepted shop open/close already invoke the bound input suspension callback in the session. Combat rejection now leaves ongoing keyboard controls intact and still displays the original rejection notice. Real shop/pause boundaries still require input release. No aim, attack radius, damage, action lock, buffer duration, skill, enemy or other-hero change.
