# 技术与制作计划

## 当前骨架

`scenes/main.tscn` 提供静态白盒场景；`scripts/main.gd` 仅负责启动标记和退出。没有提前实现技能、等级、存档、网络协议或完整游戏。当前兼容渲染器仅用于降低初始化门槛，不代表最终画面方案。

## 下一任务：工具闭环与风厉白盒

先补齐 Library 基线和真实 MCP 接入。在平台支持的 MCP 客户端中分别查询运行中的 Godot/Blender；通过 MCP 创建最小场景与动画，保存、重开、读取关键帧，并运行后获取可见证据。没有真实工具调用就不得宣布接通。

然后单独交接风厉单人战斗验证：先核实附件中的输入和招式，再定义移动、攻击、受击、一个训练目标的最小验收，不直接扩展六英雄。动画先占位，Blender 源资产与导出的 GLB 分离。确定动作后才制作正式资产。

## 后续边界（建议架构，尚未实现）

- 战斗模拟、玩家输入、镜头、UI 和表现反馈分离。受击反馈不能阻塞权威模拟。
- UI 使用 Godot Control、容器与信号；中文文本和键鼠焦点在真实画面验证。
- 第一幕阶段引入服务端权威判定，1–5 客户端独立镜头，不预设端口或托管供应商。
- 存档先明确保存点与数据版本，再实现写入和恢复；不能把未实现的无头启动称作专服。
- 后续资源预算依据真实客户端和专服剖析确定。用户阿里云 2vCPU/2GiB/3Mbps 仅为已知约束，本次未连接。

每个模块结束都提交代码、实际验证记录、未决项和下一模块接口；不跨阶段一次实现整款游戏。
